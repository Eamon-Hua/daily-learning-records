# MySQL 日志体系

记于 2026.11.26

三个日志分工明确：**redo log** 管崩溃恢复、**undo log** 管回滚和 MVCC、**binlog** 管主从复制和归档。redo/undo 是 InnoDB 层的，binlog 是 Server 层的。

## redo log：崩溃恢复

写数据先改内存页（Buffer Pool），页刷盘是随机 IO，太慢。改完内存先**顺序**写一条 redo log（物理修改记录："页X偏移Y的值改为Z"），再异步刷数据页——崩溃后重启，把 redo log 重放一遍，已提交的修改就都找回来了。这就是 WAL（Write-Ahead Logging）：日志先落盘，数据页后落盘。

相关配置：

```sql
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';   -- redo 总容量，8.0.30 起取代 ib_logfile_size
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

`innodb_flush_log_at_trx_commit` 三档：

- **1**（默认）：每次提交都刷盘，最安全
- **2**：提交写到操作系统缓存，宕机不丢、断电可能丢一秒
- **0**：每秒刷一次，性能最好，最多丢一秒事务

## undo log：回滚与 MVCC

修改前的旧值写入 undo log。两个用途：

1. **回滚**：ROLLBACK 或事务失败时，按 undo log 把数据恢复成旧值
2. **MVCC**：版本链就是靠 undo log 串起来的，快照读沿着回滚指针读旧版本

undo 是**逻辑日志**（记录反向操作：insert 的 undo 是 delete，update 的 undo 是反向 update）；redo 是**物理日志**（记录页的物理修改）。undo log 不会立刻删除：事务提交后放入历史列表，等没有事务再需要那个版本时才由 purge 线程清理——长事务会让 undo 一直膨胀。

参数：`SHOW VARIABLES LIKE 'innodb_undo%'`（独立 undo 表空间的数量与大小）。

## binlog：复制与归档

Server 层日志，记录所有**已提交**的 DDL 和 DML（逻辑操作）。用途：主从复制（从库重放主库的 binlog）、数据恢复（全量备份 + binlog 重放到指定时间点）、审计。

三种格式：

- **STATEMENT**：记 SQL 语句原文，日志小，但 `NOW()`、`UUID()` 这类不确定函数重放结果不一致
- **ROW**（8.0 默认）：记行级变更明细（哪一行哪个值改成什么），日志大但精确，主从复制用它
- **MIXED**：默认 STATEMENT，遇到不确定语句自动切 ROW

```sql
SHOW VARIABLES LIKE 'log_bin';              -- 是否开启，8.0 默认 ON
SHOW VARIABLES LIKE 'binlog_format';        -- 格式
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';  -- 保留时长，默认30天
SHOW BINARY LOGS;                           -- 现有 binlog 文件列表
SHOW BINLOG EVENTS IN '文件名';             -- 查看文件里的事件
```

## 三者怎么配合（一次 UPDATE）

1. 写 undo log（存旧值）
2. 改 Buffer Pool 里的数据页
3. 写 redo log（prepare 状态）
4. 写 binlog
5. redo log 改为 commit 状态 —— **两阶段提交**

两阶段提交保证 redo 和 binlog 一致：崩溃恢复时 redo 处于 prepare 且 binlog 完整，则提交；binlog 不完整则回滚。没有这一步，主库靠 redo 恢复了而 binlog 里没有这条，主从数据就分叉了。

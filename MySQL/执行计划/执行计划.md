# MySQL 执行计划 EXPLAIN

记于 2026.11.24

SQL 慢不慢、索引用没用上，不看猜，看 EXPLAIN 的输出。在 SELECT 前面加 `EXPLAIN` 就行，语句不真正执行，只给执行计划。

## 输出的关键列

EXPLAIN 返回十几列，重点盯这几列：

| 列 | 含义 |
|---|---|
| id | 查询序号，判断执行顺序 |
| select_type | 这一段查询的类型 |
| type | 访问方式，**最重要的列** |
| possible_keys | 可能用上的索引 |
| key | **实际用上的索引**，NULL 就是没用索引 |
| key_len | 用的索引长度，判断联合索引用了前几列 |
| rows | 预估扫描行数，越少越好 |
| filtered | 按条件过滤后剩余的行百分比 |
| Extra | 附加信息，好提示和坏提示都在这 |

## id：谁先执行

- id 相同：从上往下执行
- id 不同：大的先执行（子查询先于外层）
- id 为 NULL（UNION 结果合并段）：最后执行

## type：访问方式分级

从好到坏：

| type | 什么时候出现 |
|---|---|
| system | 表只有一行 |
| const | 主键或唯一索引等值查询，最多一条 |
| eq_ref | JOIN 时用主键/唯一索引关联，被驱动表最多一条 |
| ref | 普通索引等值查询 |
| range | 索引范围查询（>、<、BETWEEN、IN、LIKE '前缀%'） |
| index | 扫整棵索引树，比全表扫好一点 |
| ALL | **全表扫，优化目标就是消灭它** |

日常 OLTP 查询至少到 range，核心查询到 ref 以上。线上报表跑出 ALL，先想加索引或改写法。

## key_len：联合索引用了几列

联合索引 (a INT, b INT, c CHAR(10))，key_len = 4 用了 a，= 8 用了 a+b。INT 4 字节、BIGINT 8 字节、CHAR(10) utf8mb4 下 40 字节，可空列再加 1。用这个列能确认最左前缀到底命中到哪一截。

## Extra：好提示和坏提示

好的：

- **Using index**：覆盖索引，查询的列全在索引里，没回表
- **Using index condition**：索引条件下推（ICP），先把条件下推到存储引擎过滤

坏的（都要优化）：

- **Using where**：在 server 层再过滤了一遍，配合 ALL 出现说明没索引可用
- **Using filesort**：排序没走索引，内存或磁盘里额外排了一遍，数据量大时很慢
- **Using temporary**：建了临时表（常见于 GROUP BY / DISTINCT 没走索引），比 filesort 更差

## 一个完整的排查例子

```sql
EXPLAIN SELECT * FROM emp WHERE deptno = 10 ORDER BY salary;
```

如果 type=ALL + Using filesort：等值条件没索引、排序也没索引。建联合索引 (deptno, salary) 后再 EXPLAIN：type=ref、Extra 变成 Using index condition 或消失，两个问题一次解决——等值列放联合索引最左，排序列放后面，ORDER BY 直接沿索引顺序读，filesort 消失。

注意 EXPLAIN 的 rows 是**估算值**（基于统计信息），表刚大批量写入后跑 ANALYZE TABLE 刷新统计，估算更准。

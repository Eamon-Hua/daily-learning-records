# MySQL 索引操作与失效场景

记于 2026.11.23

索引建不建是设计问题，建完**用不用得上**取决于 SQL 怎么写。本篇记索引的增删查操作和索引失效的写法。

## 基本操作

```sql
CREATE INDEX idx_name ON emp(ename);          -- 建
ALTER TABLE emp ADD INDEX idx_name(ename);    -- 等价写法
SHOW INDEX FROM emp;                          -- 查
DROP INDEX idx_name ON emp;                   -- 删
```

`SHOW INDEX` 结果里重点看三列：Key_name（索引名）、Column_name（索引列）、Cardinality（大致的去重基数，越大越值得建索引）。表大了再加索引会锁写，生产环境选低峰期。

## EXPLAIN：验证索引用没用上

```sql
EXPLAIN SELECT * FROM emp WHERE ename = '张三';
```

只盯三个字段：

- **type**：访问方式，从好到坏大致是 system > const（主键/唯一等值） > ref（普通索引等值） > range（范围） > index（扫全索引） > ALL（全表扫）。**看到 ALL 就该警惕**
- **key**：实际用上的索引，NULL 就是没走索引
- **rows**：预估要扫的行数，越少越好

## 索引失效场景

索引在不在手边，看 SQL 怎么写。以下每条都是实测能复现的：

**1. 左模糊**。`LIKE '%三'` 索引用不上，因为 B+ 树按前缀排好的，不知道开头就没法定位。`LIKE '张%'` 能走索引——右模糊没事，左模糊用不了索引。

**2. 列上套函数或运算**。`WHERE YEAR(created) = 2026`、`WHERE salary + 1000 = 6000`，索引存的是列本身的值，包一层之后每行都要算，优化器直接放弃全表扫。等价改写：`WHERE created >= '2026-01-01' AND created < '2027-01-01'`，把函数从列上挪到常量那边。

**3. 类型转换**。phone 是 VARCHAR，写 `WHERE phone = 13800000001`（不带引号），MySQL 隐式把列转成数字比较，索引用不上。**值的类型和列的类型对齐**，字符串加引号。

**4. 不满足最左前缀**。联合索引 (a,b,c)，WHERE 只有 b 或只有 c，用不上。命中了 a 但 b 用运算（见第 2 条），c 也断掉——最左前缀是"连续命中"，中间断一截，后面全失效。

**5. OR 两边有一边没索引**。`WHERE ename = '张三' OR age = 18`，age 没索引就得全表扫，ename 那半的索引也用不上。要 OR 就保证两边都有索引（InnoDB 会走 index_merge）。

**6. 不等于与 NOT IN**。`!=`、`<>`、`NOT IN` 通常走不了索引——它们要"除了这些"的所有数据，范围太大不如全扫。偶尔数据量小时优化器也会用，以 EXPLAIN 结果为准，别死记。

## 一条原则

优化器是**按成本算的**，不是按"有没有索引"：表里就 3 行数据，全表扫比走树还快，有索引也不用。判断索引行为以 EXPLAIN 结果为准。

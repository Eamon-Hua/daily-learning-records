# MySQL 索引概述与分类

记于 2026.11.23

索引就是**给表建的目录**：没索引查数据全表扫，一行行翻；有索引走 B+ 树，几层跳转直接定位。代价是占磁盘、拖慢写入（每次写数据还要顺手维护索引）。

## B+ 树为什么快

InnoDB 的索引长成 B+ 树：

- 树高 3 层左右就能装千万级行——非叶子节点只存键和指针，一个 16K 的页能塞几百个键，扇出极大
- **所有数据都在叶子节点**，非叶子节点只管路标，所以任何查询都是从根到叶的固定路径，性能稳定
- 叶子节点之间用**双向链表串起来**，范围查询（BETWEEN、>、ORDER BY）顺着链表扫就行，不用回头重新走树

对比记忆：二叉树扇出太小树太高；B 树数据散在各层节点，范围查询要中序回溯；哈希表只能等值查，范围查询直接废。B+ 树矮、叶子成链，两个缺点全避开。

主键建议**自增**：新数据永远往最右边的叶子追加，页总是满的；用随机 UUID 做主键，插入位置随机，页写满就分裂，树越拆越碎。

## 聚簇索引与二级索引

- **聚簇索引**：主键索引，叶子节点存的是**整行数据**，表本身就是它（所以 InnoDB 必须有主键，没指定就偷偷造一个）
- **二级索引**（非主键索引），叶子节点存的是**索引列的值 + 主键值**。查别的字段还得拿主键回聚簇索引再查一遍，这叫**回表**

所以"SELECT * 走二级索引"至少两次查找，这就是为什么有覆盖索引这种优化（后面索引操作那篇写）。

## 分类

| 分类 | 建法 | 特点 |
| :--- | :--- | :--- |
| 主键索引 | PRIMARY KEY | 唯一 + 非空，每表只能一个，就是聚簇索引 |
| 唯一索引 | UNIQUE | 值不许重复，NULL 可以有多个 |
| 普通索引 | INDEX | 纯加速，没约束 |
| 全文索引 | FULLTEXT | 文本关键词搜索，中文要配 ngram |
| 联合索引 | INDEX(a,b,c) | 多列一个索引，**最左前缀原则**管着它 |

联合索引的规则单独记：索引按 a、b、c 顺序排好，查询必须**从最左列开始连续命中**才能用上——WHERE b=1 用不上；WHERE a=1 AND c=1 只用了 a 这一段。可以把它想象成字典先按首字母再按第二个字母排序：跳过首字母直接查第二个字母，只能全翻。

InnoDB 里哈希索引是自适应的，用户管不了；日常建的都是 B+ 树索引，别混淆。

全文索引补一句踩坑：`MATCH(列) AGAINST('关键词')` 的查询写法不难，但**小表上刚建好的全文索引经常搜不出结果**（索引缓存没同步完），多插几行真实数据、或过一会儿再查就好了。别因为搜不出来以为语法错了。

# MySQL 锁机制

记于 2026.11.25

锁解决并发读写的数据一致性问题。按粒度分三层：全局锁锁整个实例、表级锁锁整张表、行级锁锁单行（InnoDB 支持，MyISAM 只有表级锁）。

## 全局锁

```sql
FLUSH TABLES WITH READ LOCK;   -- 全库只读，DML 和 DDL 都被阻塞
UNLOCK TABLES;
```

用途：逻辑备份期间保证数据视图一致。InnoDB 有更好的替代：`mysqldump --single-transaction` 用 MVCC 快照备份，不阻塞业务。

## 表级锁

```sql
LOCK TABLES emp READ;     -- 表读锁：自己只能读，别人也只能读
LOCK TABLES emp WRITE;    -- 表写锁：自己读写，别人全阻塞
UNLOCK TABLES;
```

元数据锁（MDL）是隐式的：查询加 MDL 读锁，DDL 加 MDL 写锁。MDL 读锁之间兼容；有一个长事务持有读锁时，DDL 请求排队，**排在它后面的所有查询也全部排队**——线上改表结构前先查长事务。

意向锁（IS/IX）：InnoDB 加行锁前先在表上登记意向，用于快速判断表里有没有行锁，与行锁不冲突，不用管。

## 行级锁（InnoDB）

行锁加在**索引记录**上，分三种：

- **Record Lock**：锁单条索引记录
- **Gap Lock**：锁索引记录之间的间隙，防止插入，解决幻读（RR 隔离级别下才有）
- **Next-Key Lock**：记录锁 + 前面的间隙，RR 级别下等值/范围查询的默认加锁方式

查询走索引才用行锁，**条件列没有索引时行锁升级为锁全表**（所有记录加锁），等于全表锁——这是"update 慢还全表被锁"的直接原因。

悲观锁与乐观锁：

- **悲观锁**：假设冲突会发生，查询时直接加锁占住：`SELECT * FROM emp WHERE id=1 FOR UPDATE`，事务提交才释放。库存扣减、秒杀这类写冲突高的场景用
- **乐观锁**：假设冲突少，不加锁，更新时带版本号校验：

```sql
UPDATE emp SET salary = 6000, version = version + 1
WHERE id = 1 AND version = 5;   -- 影响行数为0说明别人改过，读新数据重试
```

## 共享锁与排他锁

```sql
SELECT ... FOR SHARE;    -- 共享锁（S锁）：其他事务能读（也加S锁），不能改
SELECT ... FOR UPDATE;   -- 排他锁（X锁）：其他事务读写都阻塞
```

普通 SELECT 不加任何锁（MVCC 快照读）。锁的等待超时由 `innodb_lock_wait_timeout`（默认 50 秒）控制，超时报 1205 错误。

## 排查锁等待

```sql
SELECT * FROM performance_schema.data_locks;         -- 当前持有的锁
SELECT * FROM performance_schema.data_lock_waits;    -- 谁在等谁
```

并发行为需要两个会话才能演示：会话 A 开事务对某行 FOR UPDATE 不提交，会话 B 对同一行 FOR UPDATE 就会等待。单连接内能看到的是已持有的锁记录。

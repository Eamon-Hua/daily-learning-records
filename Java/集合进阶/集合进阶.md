# Java 集合进阶

记于 2026.11.23

Collections 是操作集合的工具类，排序是里面最常用的一块。排序的核心问题就一个：**凭什么说谁大谁小**，Comparable 和 Comparator 就是两种回答方式。

## Collections 工具类

全是静态方法，直接类名调：

```java
Collections.sort(list);              // 排序（要元素自己能比）
Collections.reverse(list);           // 反转
Collections.shuffle(list);           // 洗牌，随机打乱
Collections.max(list);               // 最大值
Collections.min(list);               // 最小值
Collections.swap(list, 0, 2);        // 交换两个位置
Collections.fill(list, "x");         // 全部填充成x
```

还有两个"只读保护"的：

```java
List<String> 只读 = Collections.unmodifiableList(list);   // 再add就抛异常
Collections.addAll(list, "a", "b", "c");                  // 批量加，比一个个add省事
```

## Comparable：自己定规矩（自然排序）

类实现 Comparable 接口，重写 compareTo，**规矩写死在类里**：

```java
class 学生 implements Comparable<学生> {
    int 分数;

    @Override
    public int compareTo(学生 o) {
        return this.分数 - o.分数;    // 负数=我小，0=相等，正数=我大
    }
}
```

返回值含义就一句话：**负的在前面**。this 减 o 是升序，o 减 this 是降序。

写完之后 Collections.sort(list)、TreeSet、TreeMap 都自动认这个规矩。String、Integer 这些 JDK 类都实现了 Comparable，所以直接 sort 就能排。

减法写法有个坑：分数差距大到溢出时结果会反，稳妥写法是 `Integer.compare(this.分数, o.分数)`。

## Comparator：外部定规矩（定制排序）

不改动类本身，比较逻辑写在外面，想怎么比就怎么比：

```java
Collections.sort(list, new Comparator<学生>() {
    @Override
    public int compare(学生 a, 学生 b) {
        return b.分数 - a.分数;    // 分数高的在前，降序
    }
});
```

同一个类可以写 N 个 Comparator：按分数排、按年龄排、按名字排，互不影响。**类已经写死 Comparable 又想换个维度排**，也只能靠 Comparator。

用得多就记住 list.sort() 这个写法，lambda 一行：

```java
list.sort((a, b) -> a.分数 - b.分数);
```

## 两个怎么选

- 排序规矩只有一种、自己写的类 → Comparable
- 规矩经常变 / 排系统类（没源码改不了）→ Comparator

实际开发里 Comparator 用得多，因为需求一变排序就得变。
